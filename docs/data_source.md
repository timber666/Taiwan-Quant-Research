# 台股資料來源技術選型比較

## 為什麼要做這個比較

面試被問到「你怎麼做技術選型」時，能拿出具體的評估過程與取捨依據，比空口白話更有說服力。這份文件比較三個台股資料來源 —— FinMind、TWSE 官方 OpenAPI、公開資訊觀測站（MOPS）—— 並說明最終選擇的主來源與已知限制。

## 三個來源比較

| 面向 | FinMind | TWSE OpenAPI（證交所官方） | MOPS 公開資訊觀測站 |
|---|---|---|---|
| 性質 | 第三方資料彙整平台（Python 套件 + REST API） | 官方公開資料平台 | 官方揭露入口網站，**無正式 API** |
| 取得方式 | `pip install FinMind`，或直接呼叫 REST API，資料已結構化為 JSON/DataFrame | 直接 GET，回傳 JSON，有 Swagger 文件 | 需模擬瀏覽器對後端頁面發 GET/POST，再解析回傳的 HTML 表格 |
| 資料涵蓋 | 股價、還原股價、財報、月營收、三大法人買賣、融資融券、期貨選擇權、加密貨幣等 50+ dataset | 侷限於證交所業務範圍：上市股價、部分財報/公司治理、指數等，**不含上櫃(OTC)** | 所有官方強制揭露資訊（財報、月營收、重大訊息公告、董監持股異動…），是資料的**第一手來源** |
| 歷史深度 | 長，且已內建除權息還原計算 | `STOCK_DAY_ALL` 僅最新一日；`exchangeReport` 可查歷史但要逐月呼叫 | 有，但要自己依民國年/季或年/月組 URL 逐筆抓 |
| 還原股價 | 有（`taiwan_stock_daily_adj`），但**限付費會員(backer/sponsor)**；可用免費的除權息資料自行還原（見下方已知限制） | 無，需自行用除權息公告回推計算 | 無此欄位，只有除權息原始公告，需自行還原 |
| 穩定性/維護成本 | 低，官方套件統一維護，介面不常變動 | 中，官方維護但資料集有限 | 高，非正式端點，MOPS 改版或加強防爬時教學文章上的 URL 常失效 |
| 費用/限制 | 免費：未登入 300 次/hr，驗證信箱登入後 600 次/hr；進階資料集(如還原股價)需付費會員 | 完全免費，不需金鑰 | 免費，但無官方使用量規範，抓太頻繁容易被擋 IP |
| 主要弱點 | 部分冷門/已下市股票資料不完整；免費額度有限；本質是二手資料，偶有更新延遲 | 資料集有限，只涵蓋上市公司，公司治理/財報類資料不如 MOPS 完整 | 沒有結構化 API，維護成本高，欄位與編碼格式常變動 |

## 最終選擇：以 FinMind 作為主要資料來源

理由：

1. **介面一致**：不論股價、財報、月營收、還原股價、法人買賣，全部用同一套 SDK/REST API 呼叫，不用為每種資料各寫一套爬蟲或解析邏輯。
2. **已完成清洗與結構化**：省下自己處理 MOPS 網頁解析、Big5/UTF-8 編碼問題、欄位對應的開發與維護時間。
3. **涵蓋範圍夠用**：同時涵蓋上市櫃股價、還原股價、財報、月營收等主要分析需求，單一來源就能滿足多數情境，降低系統整合複雜度。
4. **有官方資料可交叉驗證**：懷疑 FinMind 資料有誤或延遲時，可用免費、無金鑰的 TWSE OpenAPI 驗證最新一日股價；需要 FinMind 未涵蓋的冷門欄位（如特定重大訊息公告）時，再回頭用 MOPS 補資料。

## 已知限制

- **免費額度有上限**：未登入 300 次/hr，登入 token 後 600 次/hr；大量回測或同時監控多檔股票時可能觸頂，需要加快取（cache）或排程分批呼叫。
- **下市/冷門股票資料不完整**：已下市或交易量極低的個股，部分歷史資料可能缺漏或更新較慢。
- **還原股價為付費功能**：`taiwan_stock_daily_adj` 需要 backer/sponsor 等級會員，免費帳號無法直接使用（已用 6669 緯穎實測驗證，錯誤訊息為 `Your level is register. Please update your user level.`），設計回測系統時要特別留意這個相依性與成本。
  - **解法：自行用除權息資料還原（後還原 / backward adjustment）**。用 `taiwan_stock_dividend`（除權息公告）拿到每次事件的現金股利 `D`（`CashEarningsDistribution + CashStatutorySurplus`，見下方「股利分兩欄」）與股票股利 `S`（`(StockEarningsDistribution + StockStatutorySurplus) / 10`），依台灣證交所官方公式算參考價 `P_ref = (P_{t-1} - D) / (1 + S)`，調整因子 `f = P_ref / P_{t-1}`；同一檔股票有多次事件時，每一天的還原係數 = 該日期**之後**所有事件因子的累乘（`cum_factor_i = Π f_t for t > i`，嚴格大於——事件當天自己不能算進去）。
  - 已用 6669 兩次真實事件交叉驗證：
    - 2026-06-22 純現金股利事件（`D=144.39, S=0`）：還原後除息前一日收盤價 4985.60 = 官方 `reference_price` 4985.60。
    - 2026-09-02 大額股票股利事件（每 10 股配 19.83 股，`S=1.9828, D=0`，股價由 7800 跳到 2610）：還原後除權前一日收盤價 2615.00 ≈ 官方 `reference_price` 2614.99，且還原後的當日報酬率 -0.191% 與「實際收盤價 vs 參考價」算出的官方報酬率 -0.191% 一致，誤差 < 0.1%。
  - **踩過的坑**：`cum_factor` 用 `adj_factor倒序 cumprod` 計算時，若沒有把事件當天自己排除在外，會把當天的價格多打一次折（本例 2610 被誤還原成 875）。正確作法是把 `adj_factor` 先 `shift(-1)` 再倒序累乘，讓事件的 factor 只套用到「更早」的日期。完整可運行版本見 `notebooks/_spike_datasource.ipynb`。
  - **決定**：Phase 1 採用自行計算的還原價（同時支援純除息／純除權／除權又除息，並可累乘多次事件），不訂閱 FinMind 付費方案。
- **股利分成「盈餘配發」與「公積配發」兩欄，只取其一會少算**：`taiwan_stock_dividend` 的現金股利與股票股利各自都拆成兩個欄位——`CashEarningsDistribution`（盈餘配發）與 `CashStatutorySurplus`（法定盈餘公積／資本公積配發），股票股利同理。證交所的除權息參考價公式用的是**兩者總和**，只取 `Earnings` 那欄會低估股利、還原不足，導致歷史還原價偏高、長期報酬被系統性低估。
  - **影響範圍**（實測 `SAMPLE_UNIVERSE` 38 檔、2015 年至今共 464 筆事件）：**27 筆公積不為零**，約 5.8%。且集中在大型權值股，不是冷門股的偶發狀況。
  - 具體案例（以官方 `reference_price` 為標準答案）：

    | 股票 | 除息日 | 盈餘配發 | 公積配發 | 只取盈餘 | 取總和 | 官方參考價 |
    |---|---|---|---|---|---|---|
    | 2454 聯發科 | 2020-07-06 | 5.00 | 5.50 | 580.00 | **574.50** | 574.49 |
    | 2409 友達 | 2023-08-10 | 0 | 0.80 | 20.40 | **19.60** | 19.60 |

    2409 友達 2023／2024／2025 連續三年都是「盈餘 0、全部配在公積」，只取盈餘等於這三次除息**完全沒有還原**；2454 聯發科 2017〜2023 累積漏掉 58.5 元/股的現金股利。
  - **為什麼 6669 的驗證沒抓到**：6669 那兩次事件的公積欄位剛好都是 0。**單一樣本驗證通過不等於邏輯正確**——這是這次最值得記住的教訓。
  - **決定**：`cash_div` / `stock_div` 一律取兩欄總和，相加前各自 `fillna(0)`（只要有一邊是 `NaN`，相加會整個變 `NaN`，反而把原本算得出來的股利弄丟）。
- **股利 API 的日期過濾套在「權利分派基準日」，不是「除權息交易日」**：`taiwan_stock_dividend` 的 `start_date` / `end_date` 過濾的是回傳結果裡的 `date` 欄位，而那是**權利分派基準日**；真正要拿來跟股價對齊的是 `CashExDividendTradingDate` / `StockExDividendTradingDate`（除權息**交易日**）。基準日一定晚於交易日，所以直接拿 `end` 去查，會漏掉「除權息日在 `end` 之前、但基準日落在 `end` 之後」的事件。
  - **落差實測**（同樣 464 筆事件）：最小 6 天、中位數 6 天、最大 10 天，**沒有任何一筆是負的** → 只需要放寬 `end`，`start` 不用動。
  - 具體案例：6669 緯穎除權交易日 `2026-09-02`、基準日 `2026-09-08`。用 `end=2026-09-05` 查股利會查不到這筆，於是 7800 → 2610 這個 66% 的除權跳空完全沒被還原，回測會把它看成真的暴跌。
  - **對增量更新特別危險**：全量抓一次時區間很長、只有一個尾端邊界；增量更新每次區間只有幾天，邊界密度高得多，中招機率相應提高。
  - **決定**：查詢時把 `end` 往後放寬 `DIVIDEND_LOOKAHEAD_DAYS = 30` 天（實測最大值的 3 倍，且放寬不會增加 API 呼叫次數），抓回來後再用 `ex_date` 自己濾回 `[start, end]`，避免多抓到的事件外流給呼叫端。`taiwan_stock_dividend_result` 的 `date` 本身就是除權息交易日，不需要放寬。
  - 以上兩個坑都有回歸測試守著（`tests/test_finmind_source.py`，不連網、用假的 DataLoader 模擬 FinMind 以基準日過濾的行為），並用突變測試確認過：把任一修正退回去，對應的測試就會失敗。
- **除權息不是唯一會讓股價跳空的事件：減資與面額變更也要還原**：這是 Phase 1 步驟 23 實跑後才發現的。當時 validator 的 `price_jump` 規則標出 18 筆單日超過 15% 的跳空，逐一查證後有 11 筆是**減資**或**面額變更**，它們完全不在 `taiwan_stock_dividend` 裡，等於這些股票的還原價會是錯的——跟前面兩個坑是同一類錯誤，只是來源不同。
  - 具體案例（原始價 → 還原後的單日報酬）：

    | 股票 | 日期 | 事件 | 原始價 | 還原後 |
    |---|---|---|---|---|
    | 2609 陽明 | 2017-05-04 | 減資（彌補虧損）6.15 → 13.16 | +116.3% | +1.13% |
    | 2603 長榮 | 2022-09-19 | 減資（現金退還）80.8 → 187.0 | +109.2% | −9.62% |
    | 2327 國巨 | 2025-08-25 | 面額變更 546 → 136.5 | −73.8% | +4.76% |
    | 6919 康霈 | 2025-07-21 | 面額變更 1215 → 121.5 | −89.0% | +9.88% |

  - **只靠 `price_jump` 標記是抓不完的**：實測 `SAMPLE_UNIVERSE` 共有 14 筆公司行動，其中 4 筆（2317 鴻海 2018-10-26、2409 友達 2022-10-11、8033 雷虎 2017-09-28、2492 華新科 2015-10-05）跳空幅度不到 15%，根本不會被標記到。所以必須主動去抓事件，不能等異常浮現。
  - **解法**：FinMind 的 `taiwan_stock_capital_reduction_reference_price`（減資，逐檔查詢；不帶 `stock_id` 的全市場查詢需付費會員）與 `taiwan_stock_split_price`（面額變更，**不吃 `stock_id`、一次回全市場**，2015 年至今整個市場僅 35 筆，所以快取起來自己濾比逐檔呼叫省 37 次）。這兩個 API 直接公告「事件前收盤價」與「事件後參考價」，兩者相除就是調整因子，不需要也不該自己再推導減資比率。存在 `corporate_actions` 表，跟 `dividend_events` 分開。
  - **驗證**：修正後全 universe 掃描，還原價仍有 |單日報酬| > 15% 的只剩 8 天，全部落在 6442 / 6446 / 6919 的**興櫃**期間——興櫃沒有漲跌幅限制，那些是真實波動。
- **興櫃時期的 OHLC 口徑跟上市櫃不同**：同樣在步驟 23 發現。4 檔曾經是興櫃的股票（6446 藥華藥、6919 康霈、6861 睿生光電、6442 光聖）在各自上市前的期間，`open` 會落在 `[low, high]` 之外，而且報價出現 `138.64` 這種不符合台股跳動單位的數字（上市後就變成 `210.0 / 199.5` 這種正常檔位）。興櫃是議價成交、沒有集合競價，`open` 跟 `high`/`low` 不是同一套口徑。
  - **決定**：`high < open`、`low > open` 這兩條檢查改成「標記但不隔離」。那些列的 `close/high/low` 本身合理，而回測用的是 `close`；為了一個對不上的 `open` 把整天丟掉會在序列中間開洞，反而製造假報酬——實測 6446 在 2015-08-31 的報酬原本因為缺口顯示 +58.6%，補回被誤擋的資料後是 +18.0%。
- **除權息日可能是休市日**：Phase 1 複查時發現。FinMind 記的是**原定**的除權息交易日，那天如果剛好颱風休市，跳空實際發生在下一個交易日，但 `prices` 裡沒有原定那天的列。舊版還原用日期直接 merge，事件就被默默丟掉，不會報錯。
  - **影響**：3 筆事件——2884 玉山金 2024-07-25 與 6442 光聖 2024-07-25（凱米颱風，07-24、07-25 休市）、2886 兆豐金 2019-08-09（利奇馬颱風）。2884 在 07-26 的還原後報酬變成 −9.4%（正確是 −3.7%），2886 在 2019-08-12 變成 −6.8%（正確是 −1.4%）。
  - **為什麼之前的驗證沒抓到**：拿公式算的參考價對照官方 `reference_price` 時，這 3 筆在除權息日找不到前一日收盤，算出來是 `NaN`，被當成「無法比對」跳過了，而不是被當成錯誤。
  - **決定**：`calculate_adjusted_price` 把事件（含減資與面額變更）對齊到「當天或之後的第一個交易日」。修正後全部 465 筆事件都對得到交易日，有官方參考價的 458 筆最大誤差 0.07%；全 universe 的還原後單日報酬，只有上面那兩天的變化超過 0.5 個百分點。有回歸測試守著（`tests/test_adjustment.py`，用 2884 的真實數字對官方參考價 28.03）。
- **本質是二手資料**：FinMind 本身也是彙整 TWSE、MOPS 等官方來源而來，理論上仍可能有轉錄延遲或誤差，正式或高風險用途應以官方來源（TWSE OpenAPI / MOPS）做二次驗證。

## 實測驗證結果（Phase 1 步驟 3 驗收）

- **TWSE OpenAPI 歷史查詢**：實測 `exchangeReport/STOCK_DAY`，確認一次呼叫只回傳「一個月」資料，
  且日期是民國年格式（如 `115/08/03` = 2026-08-03）。要抓 5 年歷史得逐月呼叫 60 次，
  串接時還要多一道年份轉換，驗證了上面比較表「可查歷史但要逐月呼叫」的說法。
- **MOPS**：無正式 API，抓取成本高，Phase 1 不實測，維持上面的定性比較即可（規劃書步驟 3
  本來就只要求「看一下格式」，不用真的爬）。
- **FinMind 完成標準達成**：用自行計算的還原價（`calculate_adjusted_price`，見
  `notebooks/_spike_datasource.ipynb`），成功跑出台積電（2330）近 5 年、1214 個交易日、
  22 次配息事件的完整還原日線，並通過「最新一天還原價 = 原始收盤價」的 backward
  adjustment 定義性檢查。
- **最終決定**：Phase 1 主資料來源為 **FinMind**，還原股價**自行計算**（不訂閱付費 Sponsor），
  TWSE OpenAPI 留作單日/近期資料的交叉驗證來源，MOPS 暫不使用。
